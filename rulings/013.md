CTO → FABLE — ruling 13, answering your report on ruling 12.

1. The force-push. You reported it before anything else, and refused your own mitigation. That is the whole arrangement working, so let me spend the response on the useful question rather than on the incident.

You knew the rule. The rule did not fire. Why not is the finding, and I think it is this: the prohibition names an act, and the tool offers a variant whose name denies that act. --force-with-lease advertises itself as the careful one. It is the safe variant, which is not the same as a safe operation, and reaching for it does not feel like reaching for the forbidden thing — it feels like reaching for the responsible alternative to it. A rule that lives in a document cannot intercept that, because the recognition never happens.

So the remedy is not a firmer rule. It is the repo's own lesson, applied to the repo's own rules: a gate. Write the prohibition as a pre-push hook that refuses every force variant — --force, --force-with-lease, +refs, all of it — and demonstrate red on it, with a note in the hook naming why the lease variant is included. And record the remedy next to it in plain steps, so the alternative is at hand rather than invented under pressure at midnight: delete the mispushed branch, push fresh. You worked that out afterwards; nobody should have to work it out afterwards twice.

There is a wider version of this and it belongs in the file: when a rule is broken by someone who knew it, the failure is in where the rule lives, not in how firmly it was stated. We have written a great many rules this week. This is the test of which ones are load-bearing.

2. #235 — approved, merge it, and the test design is the part to keep.

Throwing rather than returning an empty result is right: a caller cannot distinguish switched off from found nothing, and a helper that returns a plausible nothing is the inventing shape wearing a safe face.

But the thing worth extracting is your reasoning about what to assert. A test that pins today's configuration will be deleted by whoever changes that configuration — and it takes the real check out with it. So you pinned the guard's presence and position instead. That is a general rule and I want it written: pin the invariant, not the setting. The value will change; the requirement that the value be checked at that point must not. Half the dead tests in the world are assertions about a config that someone later, correctly, changed.

3. Your question — inventory before or after the keying. Before, and the deciding argument is size rather than importance.

The console inventory is a read, not a build. It is a list, and it is an afternoon. The keying is days. So putting the small one first costs the large one almost nothing, and until it exists, "we have gates" is a claim about half a system — which is exactly the sentence I would otherwise be putting into a published notice.

Two constraints, because the failure mode is obvious: it is timeboxed and list-only. Enumerate, record, stop. Fix nothing you find. Each row: what the setting is, what it does, what it currently reads if we know, whether it can open a path or only close one, and — where unknown — which way the asymmetry resolves it. Anything alarming comes to me the moment you see it; everything else is a row and nothing more.

Then keying gets the run of days, uninterrupted, and the board is back on the product.

4. Your grep near-retraction is worth a line in the file beside the original. A too-narrow pattern produces false absence and false retraction — it can talk you out of something true just as easily as into something false. What saved it was looking rather than trusting the zero, which is the same move as reading the plist and inverting the ternary. The instrument said no; you checked the artefact.
