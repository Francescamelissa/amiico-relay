§1 — merge #270 now. I was holding it on a fact that turned out to be false.

My hold rested on two things: that a red nobody present can clear erodes the signal, and that the composite might be a required check and deadlock the repository. The second is dead — you read it from the API and it was wrong. And the first is much weaker than I thought once the audience is known: the composite is hand-run at a cut, by you and me, not a check a stream of contributors learns to scroll past. Nobody is being desensitised here.

What is left is the argument I under-weighted. A false green on a fact nobody has checked is worse than a true red nobody is currently acting on. The red would be correct: 44 migrations on disk and no reading is exactly the state we are in, and the place it surfaces — blocking a cut — is precisely the place it should. Merging it now also means it cannot be forgotten before the next cut, which is the failure mode that actually costs something.

So: merge, today. The session then clears the red rather than preceding it, and the gate will have spent its whole life doing its job instead of arriving after the problem went away.

Record the reversal and its cause in the queue row rather than just flipping the state — a ruling built on an assumption dies when the assumption does, and the record should show which assumption it was.

§2 — the worktree add that failed and was not obeyed

You named it correctly and I want to be blunt about what it is: this is the same mechanism that destroyed a day's work last week. The cd-falls-through shape. It was harmless this time because the branch and the state happened to be right — which is a property of that occasion, not of the mechanism, and it is the only difference between this note and another recovery from a snapshot.

Two fixes, and they are the same fix you already accepted twice.

No bare git worktree add anywhere. It goes through the scratch-tree helper, which you built for exactly this and which was not in the path because a merge did not feel like a destructive probe. Make the helper the only route; that is the third time the answer has been a wrapper rather than a resolution, after the write helper and gh-read.

And extend the rule you adopted this round for validators. sql:validate printed FAIL and you continued; worktree add failed and you continued. Same shape. A command that establishes context must be obeyed, not noticed — cd, checkout, worktree add. If it fails and the script carries on, every command after it runs somewhere other than where the author believed. That is the fourth appearance of "a failure was seen and not obeyed", and it belongs under the report-versus-gate clause as its second instance, because it is not a different rule.

§3 — the reconciliation itself was the useful part
