§1 — the live reading contradicts what you reported twice

You stated on 16 September and again on 19 September that both were on main and not applied to production, and the runbook's step 0 is written on that basis.

Establish how and when, from your own command history rather than from memory: every supabase db push, supabase migration up, supabase migration repair, and anything run against a linked project. Timestamps. I want the mechanism, not a conclusion.

§2 — a migration history is a claim about what ran; the schema is what ran

Do not treat those rows as proof the SQL executed. migration repair writes history without applying anything, and a history table is a record of an intention in exactly the way a migration file is. I have asked her for the catalog reading that separates the two: whether trips.currency exists, whether trips.home_currency is gone, whether profiles.home_currency is gone.

Verify the artefact, not the operation — here the artefact is the schema and the operation is the history row. This is the same rule that started this whole engagement, arriving at the last place we had not pointed it.

§3 — if it did run, the drop executed on production before its guard existed

Work through the consequence honestly. The precondition I ordered — raise unless every profile holds the default — was written on 19 September. If trip_currency_rename reached production on or about the 16th, then the irreversible drop ran against eight live accounts with no guard at all, and the check that would have caught a non-default value now cannot be run, because the column is gone.

The exposure is almost certainly nil: you established from the code that nothing ever wrote that column, so every row held the default. But almost certainly is what the guard existed to replace, and we cannot now upgrade it to certainly. Record it that way — we were right and we were also lucky, and the guard is what makes the next one not require luck.

§4 — the possibility that matters most

One explanation for how a migration reached production without anyone deciding to apply it is that a command intended for the local stack ran against a linked project. If that is what happened, it is the most important finding of the month and it outranks everything in the queue: it means the boundary we have all been assuming between your machine and the live database does not exist where we thought it did.

Establish it before you assume it. If the linked-project state can be read, read it. If your history shows a plain supabase db push with no --local, say so plainly. And until this is settled, no command that can write to a database runs at all — not locally, not in a test, not in passing. That is a hold, and it expires when you have the answer.
