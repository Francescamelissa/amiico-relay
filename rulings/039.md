§1 — prove the write helper refuses, before you trust it with the records

The write helper exists because four writes reported success and changed nothing. Its very first use is about to be the inventory row, the rulebook clauses and the queue file — load-bearing records, written through a mechanism that has never been seen to fail.

So demonstrate the red first. Hand it an anchor that cannot match and confirm it raises rather than reporting success; hand it a count assertion that is wrong and confirm the same. Commit that demonstration as a fixture, so the helper's failure path is exercised on every run and not just on the evening it was written.

Otherwise we have replaced one unverified write path with another unverified write path, and repeated the original mistake one level up — which is the exact failure the helper was built to end.

§2 — the queue file needs three things per row, or it becomes a list nobody can empty

Each item carries who raised it, what closes it — stated as an observable, not an intention — and its state: ready, in progress, or held by me. Without the second, items accumulate and nobody can retire them without asking; without the third, my holds live in chat messages again, which is the problem the file exists to solve.

And the protocol, since I cannot push: I send amendments as text, you apply them and report the resulting order back. The file decides precedence, not the most recent message. If an amendment of mine contradicts the file, the file wins until you have applied the amendment and said so.

§3 — file the new clauses under parents, not as eleven siblings

Tonight produced a lot of rulebook material, and a rulebook that grows by eleven entries in an evening starts being skimmed — which is the same failure as a list that over-counts its alarms, applied to the document that warns about it. Consolidate as you write, rather than appending and tidying later.

Four parents cover nearly all of it. Attribution — prove what refused, not that something did; a control's scope is part of the control; a refusal is attributable only against a control that succeeds without the guard. Bypass — you cannot defend a gate from inside the process that disables it; a local hook protects against mistake, only the server against intent; --no-verify, a substitute git, core.hooksPath and HUSKY=0 are four names for one effect. Interpretation — anything placed in a medium that interprets it will be interpreted; the sentinel inside its own value space, the example stored beside the record, the comment in directive syntax. Test safety — the blast radius of a test is its own subject; verifying the artefact is detection and not authorisation.

The two that do not fit a parent and should stand alone: a workaround hides a fault, a decision follows from understanding one, and a failure whose remedy is known should print the remedy.
