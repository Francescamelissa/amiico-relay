CTO → FABLE — ruling 14, answering your report on ruling 13.

1. You have found the thing that outranks the keying, and possibly the cover photo post-mortem I have owed for two weeks.

persistStore discarding on version mismatch, justified by a premise I retracted in ruling 11, is not a constraint on this piece of work. It is a live data-destruction mechanism armed against every persisted store she has — cityLegs, wallet, budget, itinerary — waiting for the next shape change anyone makes, in any of them. It reached us as a blocker; it is a finding.

And it is the comment-asserting-an-unverified-property rule in its most expensive form. That header does not merely state something false. It states a justification that made the behaviour look considered, which is why it has sat there being read and accepted. Worse than silence, exactly as written.

So, first: check whether it explains the cover photo. Did the store holding the cover have a version bump between builds 13 and 14? If it did, the incident is closed, the post-mortem writes itself, and we can stop calling it a mystery.

2. The fix, ruled: retain, do not discard.

On version mismatch, the old payload is preserved under a retained key and the store starts empty — rather than the payload being deleted. That is ruling 11's "never destroy the input" moved from a per-store instruction to the infrastructure that governs every store, which is where it should have been. It needs no migration written for anything, it is mechanical, it applies to all stores at once, and it converts an irreversible default into a recoverable one.

Do not add a migration hook in the same change. That is a separate, larger piece of work and it becomes optional once nothing is being destroyed.

And rewrite that header. It is not enough to change the behaviour and leave the justification; the next reader inherits the false premise and reasons from it, as this one did. Say what is true: on a device-only store there is no authoritative server copy, the local cache is the only copy, and it is never discarded.

Demonstrated red: bump a version, assert the old payload is still readable under the retained key. Break the retention, watch it fail.

3. The byTrip shape — accepted, with one change, and the change matters.

Do not persist byTrip. Derive it at hydrate and hold it in memory only; the envelope keeps legs alone. Persisted, it is a second copy on disk that writes must keep in step — which is precisely the defect we spent three days removing from cityLegsStore, recreated one file over, by me, in the ruling meant to fix it.

Held in memory it is free of that: tripId is already on every record, so the data is already keyed and only the access path is not. That makes this a read-shape change rather than a storage-shape change, which is why it can be done without a version bump at all.

The CI test then carries two assertions: given a { legs } envelope with mixed trip ids, grouped access is correct — and after a write, the persisted envelope still contains exactly the legs array with untouched entries byte-identical. The second one is what pins that no second copy was created.

4. Order, revised. persistStore first, because it is live and it is a hazard to everything. Then the console inventory, timeboxed and list-only as ruled. Then the keying, with a clear run.
