§1 — the reset was my fault, and I want it recorded as mine

I designed that test. I said the blast radius of a test must be its own subject, and then specified isolation on the ref — a scratch branch — while saying nothing about the tree. Rewriting a branch locally means git reset --hard to anyone implementing it, and in the main working tree that discards every uncommitted tracked edit. The rule that would have caught it was already in the book from the git stash incident: when a tool is about to move your working tree, use a second tree instead. I wrote a test that violated a standing rule of mine and handed it to you as an instruction.

File it that way. A scratch branch is not a scratch tree, and isolating one axis of a destructive operation reads as having isolated it.

The other half of the accounting: the 20:30 snapshot is why this is a recoverable evening rather than a lost day. I ordered it for a cause that turned out to be wrong — I thought the disk was failing. Preserve before you diagnose earns its place precisely because you do not know yet what you are preserving against.

§2 — you now have two explanations for one symptom, and they must partition

§A says python3 was dead and the edit scripts did nothing. §B says three resets discarded the edits. Both are true of the evening; they cannot both be true of the same file.

So partition the evidence: for each vanished edit, name which cause accounts for it, with its timestamp on the correct side of 20:37:24. A python3-killed edit never touched disk and its mtime never moved; a reset-discarded edit did touch disk and was then reverted, so the reflog covers it and the mtime tells you which. If any file is claimed by both, one attribution is wrong — two complete explanations for one event is the same overconfidence as none, and it is the attribution parent again, one level up from the hook and the server.

§3 — a step you must remember on every invocation is not a mitigation

Eighteen of forty-two calls missed DEVELOPER_DIR. That is a 43% failure rate on a manual per-call discipline, and it is not going to improve — it is the same shape as the write rule that had to stop being a rule and become a function.

Move it into the environment. Each Bash call starts a fresh shell initialised from the profile, so exporting DEVELOPER_DIR there makes it an inherited fact rather than a thing to remember, and it needs no sudo and no waiting on her. Accepting the licence properly is still the right permanent fix and I have asked her again, but it should not be what stands between you and a clean invocation.

And label it correctly when you file it: cause known, recorded, composite reporting the toolchain — that is a decision, not a workaround. The distinction is the order, not the action.
