# Ruling 038 — the bypassed control runs against the local bare remote too — a refusal is attributable only against a control that succeeds without the guard

§1 — the bypassed control runs against the local bare remote too

Both arms of the experiment point at the disposable repository, not at GitHub. The bypassed run is the one that is supposed to succeed — that is its entire purpose — and a HUSKY=0 force-push that succeeds against the real remote rewrites something real. Against a bare repo in a temp directory it costs nothing and proves exactly the same thing.

Same principle as before: the blast radius of a test is the test's own subject. It applies with more force to the arm you expect to work than to the arm you expect to be refused.

§2 — adding the control is the right instinct, and it has a name

You added it yourself and I want to be explicit about why it matters, because it is the missing half of a rule we already had. A demonstrated red proves the gate can fire. It does not prove the refusal came from the gate — a push can fail for a malformed ref, a missing remote, a permissions error, or anything else that produces a non-zero exit and a red-looking result.

A refusal is attributable to a guard only if the same action is shown to succeed with the guard removed. That is what the bypassed arm buys, and it is the thing that was absent when a server rejection got recorded as a hook rejection.

One consequence worth capturing in the write-up: after this runs, HUSKY=0 stops being a bypass we inferred from reading husky's source and becomes one we have observed. That is the evidence base for moving the control server-side, and it is stronger than the reading. Record it as observed, with both arms and their outputs, and it will still be convincing to someone reading it in six months who does not remember husky's internals.
