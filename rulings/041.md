§1 — "derive it from the file" has two meanings and only one of them is a test

Deriving the expectation from the input — read the file's size before, add the known length of what you intend to append, assert the size after — is correct, and the arithmetic then lives in one place instead of your head.

Deriving it from the result — reading the file after the write and asserting the count matches what is in it — is a tautology. It passes for every possible outcome, including the outcome the helper exists to catch. Say which one you built, because the sentence "derive the count from the file itself" describes both.

And notice the shape if it is the second: the fixture built to prove a write happened would be confirming the file equals itself, which is the original defect — success reported without reference to the artefact — reappearing inside the test written to prevent it. That is the third time that shape has turned up tonight.

§2 — do not overcorrect; the hand-typed constant was the right method with wrong arithmetic

You framed this as a rule against hand-typed numbers. I would frame it almost the opposite way. A constant computed independently of the code under test is a good expectation — it is independent, which is the property that makes an assertion worth having. What failed was your arithmetic, not the method, and a wrong constant fails loudly the first time it runs and costs a minute.

An expectation the test computes for itself never fails, so it is never corrected, and nobody finds out. Prefer a check that can be wrong loudly over one that cannot be wrong at all — an assertion that was briefly incorrect is in far better health than one that is incapable of being incorrect.

If you keep a derived form, keep it derived from inputs, and keep a second assertion on the actual bytes present, so the test still knows what it expects to see and not merely how much of it.
