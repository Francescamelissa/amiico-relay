§3 — Ruling: the FK map comes from the catalog, not from a regex over migration text

Ruling 28 was answered "from the migrations, not from memory." The standing rule is that the migrations are the intention and the catalog is the fact — not memory, but not the migration text either. Two concrete problems with the script as written:

It splits on ;, which is not a statement separator inside a $$ … $$ function body. Any migration that defines a function and then creates a table is parsed on the wrong boundaries, and you get both false negatives and mis-attributed column lists — the same failure family as the grep that could not span a prettier line-wrap.

And it continues past every column whose reference matches auth.users|profiles, then the output is used to support a claim about what isn't there. A filter that hides the matches cannot be read as an inventory. Note trips.owner_id is absent from the output, which I read as "it references users or profiles" — but that is me inferring from a silence your script created.

You already run supabase start for the pgTAP test. So: derive the map from information_schema.columns joined to pg_constraint after supabase db reset, and have the pgTAP test assert the denominator against the catalog. Then the 40 is measured, not counted by hand, and it cannot drift when someone adds a column.

§5 — Ruling on the three residuals

The sentence does not change. The data goes. Taking them in turn.

auth.audit_log_entries — delete them. An IP address tied to a named person is personal data, the security value of an auth log for a service with under ten users is close to nil, and the expensive failure is a published dated statement that can be shown false. Two facts first. Can private.erase_user actually delete from auth.audit_log_entries given the schema's ownership and grants — if not, the runbook needs a different mechanism and that changes the procedure. And does anything already purge them: I've asked her for a count by month, and if her July sign-in is still there tonight, nothing does. Note the delete will key on a field inside payload, not a column — a predicate on a JSON shape is not a predicate on a column, and it will silently match nothing the day GoTrue changes the payload. So it asserts its own effect: count before, delete, count after, raise if not zero.

trip_invites.invited_email — erase it. Capture the address before the auth delete, clear the column, count it. Separately and not blocking: an invite sent to someone who never signed up leaves their address in that table indefinitely with no retention rule at all. Raise it as its own item; don't fold it into this.

activity_log.summary — prose is not erasable, so names must not be stored as prose. Find out whether any writer interpolates a display name or an email into summary. If one does, change it to store the actor's id and render the name at read time from the profile — which is the sentinel after erasure, so the promise "your contributions stay, with your name removed" becomes structurally true instead of hopefully true. That lands before the notice publishes; it is small now and it is a backfill later. If no writer does, then the function's own DPIA comment overstates the risk and should be corrected — a list that over-counts its alarms trains its reader to discount them, and that applies to a DPIA as much as to a gate.
