# Ruling 036 — attribute the refusal without GitHub in the picture — a local bare remote; the missing clause; the scope of "protected"

---

§1 — attribute it without GitHub in the picture at all

Do not re-run a force-push variant against the real remote to work out who refused. Point a push at a local bare repository instead — git init --bare somewhere disposable, add it as a second remote, push a branch, rewrite it, force-push it. GitHub is not involved, no protected branch is involved, and any refusal that appears is unambiguously the hook's, because there is nothing else in the path that could produce one.

And you may not even need that. The pre-push hook runs before the network. A hook refusal terminates the push with no remote contact at all — no remote: lines, no To github.com:…, no round trip. A server refusal arrives as ! [remote rejected] with remote:-prefixed text. The two are distinguishable by whether the remote was reached, not by the wording of the error, and you can read that from the output you already have.

§2 — the rule this teaches, which we did not have

We had "a gate is not installed until you have seen it fail on purpose." That is necessary and it turns out not to be sufficient. A demonstrated red proves that something refused. It does not prove that the thing you built refused.

You saw a force-push rejected and recorded the guard as working. The rejection was real, the conclusion was reasonable, and the attribution was never checked — and an unchecked attribution is how two layers of protection get counted when only one is present. Put it beside its siblings: we described RLS and the catalog disagreed; we described a hooks path and core.hooksPath disagreed; we described a hook refusal and the server had done it. Three instances of one shape — the protection we describe is not always the protection we have — and this is the clause that was missing from it.

§3 — what follows if the hook turns out to be inert

GitHub's branch protection is scoped to protected branches, so every other branch has been pushed unguarded for as long as this has been true. Establish which branches are protected and say so plainly rather than assuming main is the only one that matters — stacked branches carry work too.

And note where that protection lives: a setting in a web console, changeable by anyone with the password, with no code change and nothing to review. That is the surface we already inventoried in docs/console-control-plane.md, and if branch protection is not a row in it, it should be — marked unconditional and load-bearing, because we have just discovered the codebase may be depending on it as its only defence. There is already a standing line that branch protection is never disabled to unblock a merge, not once and not briefly. That line was written when we thought it was the second layer. If it is the first, it is not a policy any more, it is the mechanism.

Install the guard properly in the husky chain if it is missing, then prove it with §1's local remote, then record which layer refused — and from here, every gate's red records what refused, not only that something did.
