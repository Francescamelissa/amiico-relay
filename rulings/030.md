§C — ruling: the pipeline-status trap, which is now the second time

You caught it the right way — you read the remote rather than trusting the exit code, and that is the rule working. But "again" is the word that matters. A trap that recurs is not a lapse in attention, it is a missing mechanism, and the rule is living in your head instead of in the repo.

The principle, so it can be written down: a filter's exit status is a statement about the filter, not about the command that fed it. git push … | grep … returns grep's verdict on the text, and grep not finding something is not git failing. Never read a pipeline's status as the operation's status.

The mechanism, in two parts. Capture and inspect separately — run the operation, take its output and its status into variables, then grep the variable; a grep used as a test gets an explicit if or a || true, never a bare place in a && chain. And put shellcheck over scripts/**.sh and .githooks/* into the composite, so the next instance is caught by the build rather than by you noticing. set -euo pipefail at the top of every script as well, but note it is not sufficient on its own — under set -e it makes the no-match case fail harder, which is why the capture-and-inspect half is the one that actually fixes this.
