§1 — verify against main, not against the pull request

Keeping the branch until the merge is verified is the right call. Be precise about what verifies it: not the PR's merged badge, and not the CI run that passed on the branch. A squash-merge produces a commit whose tree has never existed anywhere before — CI tested the branch, and what ships is main.

So: fetch, check out main fresh, confirm the expected files are present with the expected content, and run the composite there, alone, under the toolchain, with its per-gate timing recorded. Eighteen gates green on feat/ruling-029 is not eighteen gates green on main, and the difference is exactly the class of thing that has bitten us twice this evening. The artefact is the branch everyone else pulls.

§2 — two things to check before the squash

Confirm nothing is stacked on #254. Squashing collapses its commits so they never appear on main, and any branch cut from it inherits a history that no longer exists upstream — which is how #250 and #251 got into trouble the first time.

And check that no part of the record lives only in a commit message. The three ledger entries, the demonstrated reds, the toolchain note: if any of those exists as commit prose rather than as a file, the squash destroys it silently and the loss is invisible afterwards. Same rule as everything else — if it has to survive, it lives in a file.
