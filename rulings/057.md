§1 — main and production have now visibly diverged, and nothing measures it

Two migrations sit on main unapplied. That is not a problem in itself — it is normal — but it means the live schema, the code on main, and the build in TestFlight are three different things and only two of them are ever checked against each other. Nobody can currently answer "which migrations are live?" without asking a human to go and look, which is precisely the condition that produced risk 03.

Build the reading. We have the pattern twice over: rls-live-readings and the branch-protection gate. Same shape here — a recorded reading of supabase_migrations.schema_migrations, and a gate that reds when main carries a migration the reading does not list, or when the reading is missing or stale. The setting lives in the console; the assertion lives in the repo.

Make it red rather than amber. An unapplied migration is a build whose behaviour cannot be predicted from its source, and that is worth stopping a cut for. It also gives the erasure runbook something to point at: step 0 checks the reading instead of trusting that someone remembered.

§2 — "cannot be demonstrated" is a strong claim, and I think this one is wrong

You stated, rather than implied, that the drop's precondition has no red because neither the local stack nor a fresh CI reset can hold a non-default row. Stating it was right. But look again: the guard is a SQL block, and the state it needs is one update away.

Run the migrations up to the one before it, seed a profile with a non-default currency, then execute the guard and assert it raises. pgTAP will do it inside a transaction that rolls back. That is not a contrived fixture — it is the exact state the guard exists for.

This matters more than any other red we have discussed this week. It is the only assertion standing between an irreversible drop and eight live accounts we cannot see, on a database with no backups and no point-in-time recovery, applied by hand. Every other guard in the system has been seen to fail on purpose. This one has not, and it is the one protecting the thing that cannot be undone.

§3 — a check whose result a person reads is a report, not a gate

sql:validate caught the 44033 corruption. It printed FAIL and you continued. You named it correctly as the pipeline-status trap in your own hand — and that is now the third appearance of this shape, after the push exit code and the grep.

We built pipeline-status-lint for this, and it did not help, because it covers scripts in the repository and the failure happened in an ad-hoc command. So the lesson is not another lint. It is this: a gate stops things; a report informs. A validator whose failure is noticed rather than obeyed has been demoted to a report by the person invoking it.

Every validator call in your own working commands gets wired so failure halts mechanically — || exit 1, or the invocation structured so continuing is not available. Not vigilance. You have now demonstrated three times that vigilance is not the mechanism, which is exactly the argument you accepted for the write helper.

The 44033 itself is a good instance of the interpretation parent and belongs in the table. The continuing is the finding.

§4 — the rename fix lost something the old mechanism preserved for free

The executable bit is a real defect and the fixture is the right fix. The general point is worth more than the instance: I ordered temp-then-rename because it makes "failed means unchanged" true by construction, and it does. It also replaces the inode, and with it everything the old in-place write preserved without anyone naming it — mode, and potentially ownership, extended attributes and hard links.

So: copy the destination's full metadata onto the staged file before renaming, not just the exec bit, and assert it in the fixture. And take the general form: when you replace a mechanism, enumerate what the old one preserved implicitly — the properties nobody wrote down are the ones the replacement silently drops, and they surface weeks later as something unrelated.

The scratchpad pruning is the same lesson pointed the other way and your framing of it is right: a scratch location has a lifetime, and it is measured from last access, so the things at risk are exactly the ones nobody has touched. The relay clone is not scratch — it is a working copy of a record — and it belongs somewhere durable.
