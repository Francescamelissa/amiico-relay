§1 — row 40: yes, it becomes a gate — but not exit "$fails"

You are right that its text predates the gates it now carries, and right to bring it to me rather than change the instrument we both read.

The decisive argument is not today's behaviour, since nothing consumes the exit code. It is that an exit code is a contract with future callers. Nobody reads it now; the first thing that ever does — a hook, a CI job, a wrapper written in a hurry — will read 0 on a red composite and conclude success. That is the unread column again, in a different medium: a plausible-looking value nobody consumes, waiting to be consumed wrongly. We removed profiles.home_currency for exactly that reason.

But not exit "$fails". A count in an exit status is a value placed in a channel that already means something else — 126, 127 and 128+n are reserved, and a run with 127 reds would report "command not found". That is the interpretation parent, found inside the proposed fix for it. Instead: 0 for no reds, 1 for any red, and a distinct code for "the composite could not run" — because "everything passed" and "nothing was measured" must never share a value. Put the count in the output, where counts belong.

And rewrite the 2026-08-13 declaration rather than deleting it, saying what changed and why: it was written when the composite reported, and it now carries gates that block a cut. Keep the sentence that matters — clearing a cut is a human ruling — but move where that judgment lives. The exit code states the facts; the human overrides in writing. migrations-live is red today by my ruling, and that ruling is a queue row and a recorded decision, not a suppressed status. Never make an instrument lie in order to preserve the option of overruling it, because then the overruling is invisible too.

Ship it with a fixture: a red run exits 1, a clean run exits 0, a composite that cannot start exits with the third code.
