§1 — delete the keepalive, secret and workflow both

Not fix it. Delete it.

Three facts stack up. It has never succeeded — eighteen for eighteen. Its purpose was never established either: nobody has ever verified that a scheduled read prevents a free-tier pause, so it is an assumed mechanism sitting on top of a broken one. And the decisive one: a GitHub secret's value cannot be read, so you cannot establish what that credential actually is. The name says anon; the name is not the artefact, and here there is no artefact to reach for.

An unreadable credential of unknown scope, with production reach, serving a purpose it has never achieved, is not something to investigate further. Remove it and the unknown goes with it. That is cheaper and more certain than any amount of inference from a 401.

Then handle the pause risk honestly rather than by proxy: state in the inventory that the project can pause on inactivity, that nothing currently prevents it, and that waking it is a dashboard action. If a keepalive is genuinely wanted later it gets built deliberately — a named credential, minimal scope, recorded when it is set, and a demonstrated success before it is called a mechanism.

§2 — the audit's own lesson, pointed at the audit

Row 19 said established, and its artefact was "the workflow" — the file's existence. The existence of a mechanism is not evidence that it runs. That is verify-the-artefact-not-the-operation, one level up, inside the document we built to catch exactly this.

So re-read every row marked established and ask one question of each: does its artefact show the thing succeeded, or only that it exists? Rows 4 and 6 cite real ids, row 17 cites check runs, row 15 cites a live API read — those pass. Any row whose evidence is a file, a config entry, or a setting's presence does not, and gets demoted to assumed until something shows it working.

Correcting row 19 in place was right, and it is worth saying that finding it at all is the audit paying for itself within a day of being written.

§3 — eighteen silent failures

The part that should trouble us more than the credential. Eighteen consecutive failures of a scheduled job, over weeks, and no one heard. Whatever GitHub's notification path for scheduled-workflow failures is, it reached nobody — and that is the same shape as the trips banner: a failure that nobody is told about is indistinguishable from success.

Establish where those notifications went, or would have gone, and say plainly whether any unattended job on this project can currently fail loudly to a person. If the answer is no — and I expect it is — that is a finding in its own right and belongs in the audit beside row 19, because every scheduled thing we ever add inherits it.
