§1 — THE RLS LIVE READING. THE ASK IS JUSTIFIED. THE QUERY IS NOT YET SAFE.

Agreed that build 19 needs its own live RLS reading and that this is the one
item that legitimately belongs on Francesca's list. Rulings 17/20 are right
and the mechanism is not ceremony: a policy's USING or WITH CHECK expression
can name a column, 20260916200000 renamed one, and a policy left referencing
the old name is exactly the defect that has already broken the shipped client
once this month. Reading it is proportionate. Say that to her in one line when
you send it, so it does not read as more paperwork.

But DO NOT send her a query that returns one row per policy.

Twenty-three tables in public. trips alone carries four policies. At anything
like that average the result lands somewhere near ninety rows, against a SQL
editor whose display caps at a hundred and whose Export exports the view. That
is not a safe margin — it is the same cliff the first schema reading went over
on 22 September, approached from below instead of above, and a result that
stops at row 100 looks exactly like a complete one.

Prescribe it GROUPED, one row per table, the policies aggregated into the
detail column, with the result's own row count as the first row — the same
shape that worked and the same shape both gates now parse. Twenty-four rows,
nowhere near the cap, and self-verifying if it ever gets near.

Three further constraints on the text before it goes out:

  a) It returns only catalog names and policy expressions. No table in it can
     yield a person's identifier, which is the standing rule for anything sent
     to a human, and it holds here by construction rather than by care.
  b) Read RLS ENABLED from pg_class.relrowsecurity per table, not only the
     policy list. A table with zero policies and RLS off, and a table with
     zero policies and RLS on, are opposite findings and a policy-only query
     cannot tell them apart. An absent row is not a reading.
  c) The doc's prescribed fence and the text you send her must be the same
     string. Yesterday's red was precisely the gap between a reading and the
     query it claims to have run; do not reopen it from the other side.

Prescribe it in the doc first, then send me the exact text and I relay it. I
am deliberately not writing this query myself. Two queries for one reading is
two sources of truth, and the divergence is how yesterday's red happened.
