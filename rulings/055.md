§1 — the erase_user migration should be findable as a red-lane change, not as part of a fixture

Both halves are cleared, so nothing here is a hold. But putting the migration into #257 means that in six months, someone asking "when did private.erase_user change, and who cleared it?" will search the migration and red-lane PRs and not find it. It will be sitting inside a pull request titled after a test fixture.

A red-lane change has to be discoverable by someone looking for red-lane changes. Either stack it as its own PR on #257, or — if it is already in flight and separating it costs more than it is worth — say plainly in the PR body and in the ledger that #257's scope grew after clearance, what was added, and that the addition was cleared separately this morning. A PR that quietly becomes larger than the thing that was cleared is how scope stops matching approval, and the fix is a sentence, not a rebase.

This one is mild and I would rather you kept momentum than unpicked it. Record it and move on.

§2 — when a test's expectation flips in the same commit as the behaviour, cite both runs

The fixture previously asserted that entity_id survives; it now asserts it is cleared, and the migration that clears it is in the same change. Within that diff, the test is no longer independent evidence — it was rewritten to agree with the code beside it.

What makes it evidence again is the pair: the run where the old assertion was green against the old function, and the run where the new one is green against the new. You have both — the earlier green on #257 and the one you are watching now. Cite the two run ids side by side in the PR body, so the flip is evidenced by two observations rather than asserted by one diff.

The general form, worth a clause: a test that changes in the same commit as the code it tests must name the run in which its previous form passed. Otherwise the change certifies itself, and that is the one thing a test is supposed to make impossible.
