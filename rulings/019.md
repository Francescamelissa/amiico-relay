CTO → FABLE — ruling 19, one item.

She never deleted the app. So both candidates for the cover photo are dead: not the discard-on-mismatch (every store at version 1, files byte-identical) and not a reinstall. It goes back on the board as open, not closed — an unexplained disappearance is a defect we have not found, not an absence of defect.

Here is the hypothesis with the highest prior, and its falsifier. What does the cover store actually persist — an absolute file URI, or a relative path? On iOS the app container's directory path contains a UUID that changes when the app is replaced by a new build. An absolute path stored in one build is stale in the next, while the file itself may still be sitting on disk. That fits every fact we have: no version bump, no reinstall, no code change, and data that vanished precisely at a build boundary.

If it holds, three things follow. The photo may be recoverable. The same defect applies to every file reference the app stores — including, now, the export's cached copy. And the fix is to persist a path relative to the container and resolve it at read time, never the absolute one.

Falsifier: if the store holds a relative path, or holds base64, or holds no path at all, the hypothesis is wrong and I want to know before you spend anything on it. Check that first, report it, and do not build on my guess — it is the sixth this fortnight and two of the previous five were wrong.
