To Fable. Two points, both about what the count does and does not prove.

§1 — a self-reported count catches truncation, not misdefinition

The count rows and the entry rows come from the same query, so they agree whenever the query is faithfully transported — which is exactly the truncation case, and that is the case worth catching. But if the question were wrong — a where table_schema = 'public' that should have covered another schema, say — the count and the entries would be wrong together, agree perfectly, and the gate would go green on a reading that is complete with respect to a query nobody checked.

So assert both completenesses. The count proves the reading is complete with respect to its query; only pinning the query text proves the query is the one we meant. The RLS readings doc already carries its query; do the same here, and have the gate compare the query recorded beside the reading against the one the doc prescribes. Then a change of scope shows up as a change of text rather than as a silently narrower answer.

§2 — a zero count is not a valid reading

count, columns, 0 would pass a mismatch check perfectly: zero declared, zero entries, consistent. And it is our own sentinel rule — empty sits inside the value space of legitimate answers, so it cannot distinguish "the schema is empty" from "the query returned nothing". A public schema with no columns is not a state this project can be in.

Red on a zero count, with a floor and the reason beside it, the way tap-target-audit carries its 190. Same for migrations: a database with no migrations applied is not a reading, it is a failure wearing one.
